# 仿写的整稿逻辑复核

审核器绑定的是提供的稿件文件及各版口播；若原稿、素材或镜头计划存放在稿件外的独立文件，它不会自动监测这些文件。来源或镜头计划变化后应重新阅读并复核，不得声称外部文件已自动绑定。

用于在保留原视频框架的基础上仿写，特别是更换职业、人物关系、生活场景或强化情绪时。先看每个版本的**连续口播正文**，再看原稿、镜头和作者说明。人物小传、拍法备注或模型的内心设定不能代替正文中必要的交代。

逐版实际判断以下问题，并在审核记录中引用该版正文的具体短句：

1. **角色与功能**：说话人是谁、为什么关心这个问题；新职业是否能承接原片角色在故事里的作用。
2. **行动与因果**：为什么去尝试、坚持、复查或推荐；前后情绪和转折是否有依据。删掉前提后，不能留下无法理解的“漏网之鱼”等结论。
3. **关系和入口**：涉及团队、直播间、粉丝、同事等时，正文是否让人理解他们与说话人的关系、为什么参与以及从哪里来。没有相关元素的稿件可说明不适用，不要硬加。
4. **经历归属**：区分本人经历、团队测试、他人反馈和作者主张，不将一个主体的结果移给另一个主体；尊重用户已明确确认的实测归属。
5. **源稿承接**：按用户要求核对原叙事功能、时间、数量、结果及给定产品信息；加强情绪不等于加大实测结果。不要补造未给出的专家资历、机构认证或研究数字。
6. **镜头和时长**：旁白与画面功能应对应；新职业场景若原素材没有，明确要借原构图重拍。源片时长与新稿口播预计时长分开，实录后再锁成片时间。
7. **整体通读**：不看角色设定或解释，从头到尾读该版口播，判断陌生观众能否顺着事件理解；保留自然表达，删去只为出现职业词而增加的难懂比喻。

例如“摄影师→团队测试→直播招参与者”本身可以成立，但正文应交代与其相关的团队、直播间和行动理由；如果没有铺垫，应补充已知/用户授权的故事关系，或选择更适配的角色。不能因为出现“摄影师”和“直播”两个词就自动判错，也不能为了过审凭空编造真实资历。

## 记录与执行

由审阅者填写 `story-logic-review/v1` JSON。每个要交付的版本分别记录七项判断、理由和属于该版本正文的精确引文；不适用项说明为何不适用，未解决项标为 `needs_revision`。一个版本有问题时修改该版后重新通读、重新绑定哈希。优先由与作者不同的审阅者检查；没有独立审阅者时允许明确写 `same_agent_second_pass`，如实标为同人第二遍，不能假称独立。

在交付或回写仿写稿前运行：

```text
python -X utf8 <skill-dir>/scripts/story_logic_review.py --draft <draft.json> --review <story-review.json>
```

当前支持 `groups[].<版本>.parts[].text` 和 `versions: {版本: 连续口播}` 两种输入；`--versions C,D` 可明确选择本次交付的版本。审核须绑定源草稿文件与各版完整口播的SHA-256，并精确定位引文。草稿、拍法或时间改动后必须重审。完整结构见脚本顶部schema和示例测试。审核记录与诊断保存在工作证据，不插入用户的口播正文。

这个程序只检查审核记录、引文和哈希绑定；**不会自动判断故事讲得通、审阅者真正独立、产品事实真实或模型能力相同**。先有真实审稿判断，才能填写结果；程序通过不能代替审稿或实际配音、剪辑验收。
